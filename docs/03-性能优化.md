# 03 · 性能优化：2.93 s → 1.36 s

用户嫌慢，于是先 profile 再动手。结果发现**问题不在算法，在硬件没用满**。

---

## 优化前的 profile

1080×2400 长截图，26 行文字：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| det（NPU 545 ms + CPU 后处理 135 ms） | 0.68 s | 23% |
| **rec 的 NPU 推理**（27 行 × 56.5 ms） | **1.53 s** | **52%** |
| CTC 解码（27 行 × 16.1 ms） | 0.43 s | 15% |
| cls + warpPerspective | 0.19 s | 6% |

然后看了一眼 NPU 的负载：

```
/sys/kernel/debug/rknpu/load
NPU load:  Core0:  7%, Core1:  0%, Core2:  0%
```

**RK3588 有三个 NPU 核，而 `rknn_lite` 默认只绑 core0 —— 三个核只用了一个，
另外两个全闲。** 这就是最大的那一块浪费。

---

## 优化 1：三核并行（最大头）

建 3 个 `RKNNLite` 实例，用 `init_runtime(core_mask=...)` 各钉一核，
线程池把裁剪好的图分发给它们：

```python
_CORE_MASKS = [RKNNLite.NPU_CORE_0, RKNNLite.NPU_CORE_1, RKNNLite.NPU_CORE_2,
               RKNNLite.NPU_CORE_0_1, RKNNLite.NPU_CORE_0_1_2]
```

```python
out = [None] * len(crops)
lock = threading.Lock()
state = {"i": 0}

def loop(k):
    w = self.workers[k]          # 每个 worker 独占一个核上的 runtime
    while True:
        with lock:
            i = state["i"]
            if i >= len(crops):
                return
            state["i"] = i + 1
        out[i] = w.run(crops[i])
```

宽行和窄行不会被分到同一个核上。**rec 阶段 1.53 s → 0.70 s。**

> ⚠️ 注意：`NPU_CORE_0_1_2` 对**单次**推理反而更慢（一个大图铺满三核的
> 调度开销大于收益）。多核要靠「多个实例同时跑」才吃得到。

## 优化 2：CTC 解码只对选中时间步做 softmax

rec 的输出是 `(T × 6625)` 的 logits。对整个张量做 softmax 要 **12.1 ms/行**。

但 CTC 只需要**选中时间步**那个类的概率，它的分母只需要**自己那一行**的
归一化 —— 所以只需要 exp 选中的那几行（通常 20~30 行）：

```python
sub = lg[sel]                       # (K, C)，K ≈ 23
m = sub.max(axis=-1, keepdims=True)
e = np.exp(sub - m)
den = e.sum(axis=-1)
p = e[np.arange(len(sel)), idx[sel]] / den
```

**12.1 ms → 2.1 ms/行，数学上完全等价**（分子分母用的是同一个平移常数）。
整场 0.43 s → 0.08 s。

## 优化 3：det 图铺满三个核

det 是一个大图，拆到多核上有收益：

```
core0      545.1 ms
core0_1    474.9 ms
core0_1_2  449.7 ms
```

`DET_CORE_MASK=0_1_2` → **545 ms → 450 ms**。
（det 只调用一次，跑在 rec 之前，所以和 rec 的三个实例不冲突。）

## 优化 4：干掉大数组临时拷贝

`normalize` 和 `sigmoid` 都是多 megapixel 的操作，原来每次都要拷贝 2~3 份
float32 数组。改成原地算：

```python
def normalize(img):
    """(x/255 - 0.5)/0.5 == x/127.5 - 1"""
    x = img.astype(np.float32)
    x *= (1.0 / 127.5)
    x -= 1.0
    return x
```

```python
def sigmoid_if_logits(o):
    o = np.asarray(o, dtype="float32")
    if o.size and (o.max() > 1.0 or o.min() < 0.0):
        np.clip(o, -60.0, 60.0, out=o)
        np.negative(o, out=o)
        np.exp(o, out=o)
        o += 1.0
        np.reciprocal(o, out=o)
    return o
```

再加上输入 buffer 按宽度复用（多线程下分配 churn 就是 GIL 争用）。

## 剩下的天花板

单次 NPU 调用的开销可以拟合出来：

```
t ≈ 8.6 ms + 0.064 ms × 输入像素数
```

实测点：320 px → 29 ms，832 px → 60.5 ms，1024 px → 74 ms。

所以一行 1024 px 宽的文字天然要 74 ms，27 行就是 1.5 s 的纯 NPU 算力——
**这是当前模型的计算下限**。想再快只有两条路，都与「精度追平 CPU」冲突：

* int8 量化（掉精度）
* 缩小 rec 的输入宽度（错字）

---

## 附带：常驻服务

CLI 每次都是新进程，要付 **~1.9 s** 启动（python + rknnlite 导入 +
加载 3 份 rec 模型）。所以把流水线包成了 systemd 常驻服务，
模型一直热着：

| | 端到端 | 其中纯推理 |
|---|---|---|
| CLI | 2.4 ~ 3.3 s | 0.55 ~ 1.36 s |
| 服务 | 0.44 ~ 1.25 s | 同上 |

---

## 踩过的坑

* `itertools.count()` **永远不会 StopIteration**，`next(counter, None)` 拿不到
  结束哨兵 → 线程池 worker 的索引跑飞，报 `IndexError`。
  共享索引要用 `threading.Lock` + 计数器。
* RKNN runtime 噪音用 `RKNN_LOG_LEVEL=0`（环境变量）静默；
  `W rknn-toolkit-lite2 version: 2.3.2` 那三行是 import 时打的，压不掉，无碍。
