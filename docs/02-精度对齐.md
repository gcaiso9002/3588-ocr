# 02 · 精度对齐：把 NPU 做到和 CPU 逐字一致

最初的 NPU 版本**置信度普遍掉到 0.70**，还偶发错字、丢行。
查下来是三个互相独立的原因叠加，逐个修掉之后才做到 18/18、16/16 逐字一致。

---

## 坑 1（最隐蔽）：末尾的 Softmax 不能留在 NPU 上

**现象**：所有行的置信度从 0.99 集体掉到 **0.70**，而且偶尔串字。

**根因**：RKNN 编译器把模型末尾的 Softmax 编成了一个 fp16 的 NPU 算子
`exSoftmax13`。fp16 的 `exp()` 精度不够，把 softmax 后的概率分布压平了。

**解法**：**用 onnx 把模型末尾的 Softmax / Sigmoid 剪掉**，让 NPU 只输出
logits，激活函数用 numpy float32 在 CPU 上做。

```bash
# 剪掉末尾的激活
python strip_tail.py ppocr_v4_det.onnx ppocr_v4_det_logits.onnx
```

剪完置信度立刻回到 0.99，错字少了一半。
det 末尾的 Sigmoid 同理。

```python
def _to_probs(out):
    """模型是带 Softmax 编译的就被编成 fp16 算子，分布会被压平。
    我们的模型剪掉了 Softmax，这里用 float32 补回来。"""
    o = np.asarray(out, dtype="float32")
    if o.size and o.max() > 1.5:
        o = o - o.max(axis=-1, keepdims=True)
        np.exp(o, out=o)
        o /= o.sum(axis=-1, keepdims=True)
    return o
```

## 坑 2：cls 的裁剪图不能拉伸

**现象**：整行文字丢失，rec 输出空串。

**根因**：PaddleOCR 对 cls 的预处理是「**按比例缩到自然宽 + 补边到 192**」。
我最初直接 `cv2.resize(crop, (192, 48))` **拉伸**了，cls 的分数随之改变，
把一条斜排的横幅误判成 180° 并旋转——旋转后的图 rec 自然读不出东西。

**解法**：补边，不拉伸。

```python
h, w = crop.shape[:2]
ratio = w / float(h)
rw = int(math.ceil(48 * ratio))          # 自然宽
if rw > 192: rw = 192
resized = cv2.resize(crop, (rw, 48))
canvas = np.zeros((48, 192, 3), np.float32)
canvas[:, :rw, :] = resized               # 右边补零
```

改完与 CPU 一致。

---

## 坑 3：det 的输入几何必须照抄 RapidOCR

**现象**：整块横幅丢失，框的位置还差 1~3 px。

**根因**：我把图缩放后塞进了 960×960 的画布，**右侧留了 224 列黑边**。
黑边改变了 DB 的概率图，整块文字区域被吞掉。

**解法**：完全用 RapidOCR 的几何：

```python
ratio = 736.0 / min(h, w) if min(h, w) < 736 else 1.0
rh = int(round(int(h * ratio) / 32) * 32)
rw = int(round(int(w * ratio) / 32) * 32)
```

即 `limit_side_len=736`、`limit_type=min`、缩放到 32 的倍数、**四周不补边**。
改完 det 的框与 ONNXRuntime **逐像素一致**。

---

## 坑 4（补充）：rec 固定 320 宽会把宽行压扁

**现象**：宽行里出现错字（`防`→`方`）、多吐空格，长横幅读成空。

**根因**：rec 的输入宽度固定 320，一行 1080 px 宽的 50 px 高文字，
横向被压扁了 2~3 倍。

**解法**：把 rec 编译成**多宽度模型**（16 个宽度：320…1024），
运行时按 PaddleOCR 的 `ceil(48 * ratio)` 选最接近的受支持宽度。

同理 det 也编译成**多尺寸模型**（17 个输入尺寸，按长宽比吸附）。

---

## 膨胀核 `DET_DILATE=2` 是最优

| 核大小 | 效果 |
|---|---|
| 1 | 丢整块横幅 |
| **2（PaddleOCR 默认）** | **最优** |
| ≥3 | 相邻行粘在一起，并引入新错字 |

> 自己踩过的 bug：用 `== "1"` 判断「是否膨胀」时，`DET_DILATE=2` 反而把膨胀
> **关掉**了。两次运行结果不一致才抓到。现在内核尺寸就是语义。

---

## 不做的事

* **不做启发式行合并**：偏离参考实现，误合并风险高。NPU 侧 det 切行与 CPU
  有差异就如实记录。
* **不做 int8 量化**：保持 float16，`do_quantization=False`，精度优先。
* **不用 CPU det 兜底**。

---

## 残留差异

NPU 的 det 概率图与 ORT 有极小数值差（max|Δ| ≈ 0.2，mean ≈ 1e-4），
个别图相邻文字块的连通性不同 → **行数**可能不同，文字都对。

ORT 是否开图优化（`ORT_ENABLE_ALL`）也会改变这一区域。

---

## 怎么复现验收

```bash
# 板子上
cd /opt/npu-ocr
po-ocr  ch_en_num.jpg  > cpu_all.json      # CPU 基准
npu-ocr ch_en_num.jpg                      # NPU
python3 compare.py /opt/npu-ocr/ch_en_num.jpg   # 逐行 diff
```

> `compare.py` 的基准 JSON 用**绝对路径**做 key，必须传绝对路径；
> 传相对路径不会报错，只会显示 `CPU=0 lines` 全判 DIFF（假失败）。

结果：

```
=== ch_en_num.jpg   NPU=18 lines  CPU=18 lines  (0.55s) ===
   OK    假一赔十                    npu=0.997 cpu=0.997
   OK    破损就赔                    npu=0.948 cpu=0.927
   ...
   OK    正品促销                    npu=0.999 cpu=0.999
```
